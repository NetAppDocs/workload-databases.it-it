= Analisi della configurazione per ambienti di database in Workload Factory
:allow-uri-read: 
:icons: font
:imagesdir: ./media/


[role="lead"]
Workload Factory for Databases analizza regolarmente le configurazioni dei database per individuare eventuali problemi con le implementazioni di Microsoft SQL Server e Oracle su Amazon FSx for NetApp ONTAP storage. Quando vengono rilevati problemi, Workload Factory ti mostra quali sono e spiega cosa deve essere cambiato affinché le configurazioni del tuo database raggiungano prestazioni ottimali, efficienza dei costi e conformità alle best practice.

Workload Factory fornisce best practice e raccomandazioni per carichi di lavoro di database ben strutturati. L'analisi well-architected valuta le configurazioni e le impostazioni di Microsoft SQL Server e Oracle Database relative a storage, compute, applicazione, resilienza e clonazione.



[[how-it-works]]
== Come funziona

Workload Factory analizza quotidianamente i carichi di lavoro in esecuzione sulle implementazioni dei file system Amazon FSx for NetApp ONTAP. L'analisi fornisce stato ben architettato, approfondimenti e raccomandazioni.

Al termine dell'analisi giornaliera, le configurazioni vengono visualizzate come "ottimizzate" o "non ottimizzate" nella dashboard Well-architected per la distribuzione. Troverai il punteggio di ottimizzazione totale, i problemi di configurazione per categoria e un elenco di problemi di configurazione e raccomandazioni. Puoi esaminare le raccomandazioni relative ai problemi di configurazione. Alcuni problemi possono essere risolti automaticamente da Workload Factory, mentre altri richiedono un intervento manuale. In questo caso, Workload Factory fornisce istruzioni dettagliate per aiutarti a implementare le modifiche consigliate.

Puoi ignorare l'analisi delle configurazioni che non si applicano ai tuoi ambienti. Questo evita avvisi non necessari e risultati di ottimizzazione imprecisi.

Puoi anche creare regole personalizzate in linguaggio naturale per convalidare i tuoi ambienti rispetto agli standard della tua organizzazione e alle best practice di NetApp. Prova le regole con una simulazione, poi pianifica la loro esecuzione su tutti i tuoi ambienti. link:https://docs.netapp.com/us-en/console-well-architected/learn-custom-rules.html["Scopri di più sulle regole personalizzate"^].



[[why-it-matters]]
== Perché è importante

Workload Factory applica le best practice ad ambienti di storage, database e VMware di grandi dimensioni, combinando valutazioni continue con suggerimenti e interventi correttivi. Le correzioni automatiche applicate nella console di Workload Factory riducono gli errori umani, garantiscono una gestione uniforme e preservano prestazioni e affidabilità nelle infrastrutture di workload.



[[options-for-analyzing-your-database-environment]]
== Opzioni per l'analisi dell'ambiente del database

Workload Factory offre le seguenti opzioni per analizzare il tuo ambiente database:

* *Valutazione una tantum*: Esegui una link:optimize-configurations.html["valutazione una tantum"] per scoprire lo stato di corretta architettura delle tue istanze di Microsoft SQL Server o database Oracle senza memorizzare credenziali o registrare risorse.
+
Per la valutazione una tantum, devi fornire le credenziali solo una volta per le istanze di Microsoft SQL Server o i database Oracle che vuoi analizzare.

* *Valutazione continua*: Workload Factory analizza regolarmente il tuo ambiente di database, fornisce raccomandazioni continue per ottimizzare le configurazioni e risolve automaticamente i problemi.
+
Per la valutazione continua, devi registrare le risorse, associare un collegamento e concedere le autorizzazioni nel tuo account AWS.





[[microsoft-sql-server-best-practices]]
== Procedure consigliate per Microsoft SQL Server

Le seguenti best practice e raccomandazioni si applicano ai carichi di lavoro di Microsoft SQL Server.



[[storage]]
=== Storage

.Livello di archiviazione
Usa il livello SSD primario per i carichi di lavoro SQL sensibili alle prestazioni.

[%collapsible]
====
Usa il livello SSD primario per i volumi FSx for ONTAP per prestazioni ottimali. Il livello del pool di capacità potrebbe ridurre le prestazioni e aumentare la latenza. Il livello SSD primario è progettato per carichi di lavoro dalle performance elevate, mentre il livello del pool di capacità è ottimizzato per l'efficienza dei costi e potrebbe non soddisfare i requisiti di prestazioni dei carichi di lavoro di SQL Server.

====
.Headroom del file system
Mantieni abbastanza capacità libera oltre la dimensione totale del volume.

[%collapsible]
====
Assicurati di avere una capacità del file system sufficiente, superiore alla dimensione totale del volume. Troppo poco spazio libero causa problemi di prestazioni; troppo spazio spreca storage e aumenta i costi.

====
.Dimensione del disco di log
Dimensiona e monitora le unità di log per evitare rollback e interruzioni.

[%collapsible]
====
Dimensiona e monitora l'unità di log di SQL Server per prevenire annullamenti delle transazioni, indisponibilità del database, danneggiamento dei dati e problemi di prestazioni causati da un'unità di log piena.

====
.Dimensione dell'unità TempDB
Dimensiona TempDB per evitare colli di bottiglia e timeout.

[%collapsible]
====
Dimensiona e monitora TempDB per mantenere prestazioni e stabilità. Uno spazio TempDB insufficiente può causare rallentamenti delle query, timeout delle applicazioni e arresti anomali del sistema.

====
.Posizionamento dei file di dati e di registro
Percorsi `.mdf` e `.ldf` separati.

[%collapsible]
====
Separa i file di dati e di log su unità diverse per migliorare l'I/O parallelo, la flessibilità del backup e il comportamento di ripristino. Ti consigliamo di separare i percorsi LUN dei dati e dei log in volumi diversi per i database di dimensioni ridotte.

====
.Posizionamento di TempDB
Usa un'unità dedicata.

[%collapsible]
====
Posiziona TempDB su un'unità dedicata per evitare conflitti di I/O e migliorare le performance e la stabilità di SQL Server.

====
.thin provisioning
Assegna lo spazio di archiviazione quando ne hai bisogno.

[%collapsible]
====
Configura il thin provisioning per i volumi FSx for ONTAP per sfruttare al meglio lo storage e ridurre i costi. Il thin provisioning ti permette di allocare lo storage in base alle necessità invece di riservare tutta la capacità in una volta sola.

====
.Dimensionamento automatico e modalità di dimensionamento automatico
Aumenta i volumi automaticamente.

[%collapsible]
====
Attiva il dimensionamento automatico e imposta la modalità su  `grow` così i volumi aumentano automaticamente prima di diventare pieni e di sola lettura.

====
.Gestione dello spazio del dispositivo a blocchi
Configura le impostazioni dello spazio dei dispositivi a blocchi per le LUN usate da SQL Server.

[%collapsible]
====
Configura le impostazioni dello spazio dei dispositivi a blocchi per le LUN utilizzate dalle istanze di Microsoft SQL Server per prevenire errori di scrittura e migliorare l'efficienza dello spazio su FSx for ONTAP.

====
.Riserva di copia Snapshot e cancellazione automatica
Tieni spazio per i dati attivi.

[%collapsible]
====
Imposta la riserva di copie Snapshot allo 0% e abilita l'eliminazione automatica degli Snapshot per proteggere lo spazio per i dati attivi.

====
.Gestione dello spazio
Espandi il volume prima di eliminare le copie Snapshot.

[%collapsible]
====
Quando lo spazio disponibile scarseggia, espandi il volume prima di eliminare le copie Snapshot. Espandere il volume previene gli errori "volume pieno", riduce i fallimenti di scrittura e preserva i punti di ripristino Snapshot.

====
.Tiering / ottimizzazione TCO
Suddividi in livelli i dati Snapshot utilizzando la policy di tiering solo per Snapshot.

[%collapsible]
====
Utilizza la policy di tiering solo per snapshot, che sposta nel livello di capacità solo i dati degli snapshot, mantenendo i dati attivi nel livello SSD. Questo approccio preserva le performance a bassa latenza per i carichi di lavoro SQL, riducendo i costi di storage. Esegui il tiering dei dati degli snapshot dopo un periodo di raffreddamento di 7 giorni.

====
.Efficienze dello storage
Usa deduplicazione, compressione e compaction.

[%collapsible]
====
Abilita deduplica, compressione e compaction per ridurre l'uso dello storage e i costi, mantenendo le performance.

====
.Tipo OS
Abbina il tipo di sistema operativo LUN ONTAP al partizionamento dell'host.

[%collapsible]
====
Abbina il valore del sistema operativo LUN ONTAP allo schema di partizionamento dell'host per mantenere il corretto allineamento I/O.

====
.Criteri MPIO, sessioni, stato e impostazioni di timeout
Configura criteri, sessioni, stato e impostazioni di timeout per Multipath I/O (MPIO).

[%collapsible]
====
Configura Multipath I/O (MPIO) per resilienza e throughput. Usa cinque sessioni MPIO per interfaccia di destinazione per SQL Server su LUN iSCSI, monitora lo stato del percorso e imposta il timeout dell'host a 60 secondi.

====
.dimensione dell'unità di allocazione NTFS
Impostato su 64K.

[%collapsible]
====
Imposta la dimensione dell'unità di allocazione NTFS a 64K per migliorare l'efficienza del disco e ridurre la frammentazione per i carichi di lavoro di SQL Server.

====
.Snapshot locali programmati
Disabilita gli snapshot programmati.

[%collapsible]
====
Disabilita gli snapshot pianificati per i volumi FSx for ONTAP utilizzati da Microsoft SQL Server. Gestisci invece gli snapshot esternamente utilizzando strumenti come NetApp SnapCenter, che creano backup coerenti con l'applicazione e aiutano a prevenire la corruzione dei dati durante le operazioni di ripristino.

====

=== Applicazione

[%collapsible]

Applica le patch più recenti di SQL Server per migliorare la sicurezza e l'affidabilità del sistema.

[%collapsible]
====

[[resiliency]]
=== Resilienza

.Snapshot coerenti con l'applicazione
Usa snapshot coerenti con l'applicazione con NetApp SnapCenter.

[%collapsible]
====
Utilizza snapshot coerenti con l'applicazione con NetApp SnapCenter per creare snapshot accurati e affidabili dei dati del tuo volume in un momento specifico. SnapCenter semplifica i backup e ti aiuta a ripristinare rapidamente i dati, riducendo i tempi di inattività e proteggendo i carichi di lavoro critici.

====
.Replicazione interregionale
Proteggi contro le interruzioni regionali.

[%collapsible]
====
Abilita la replica tra regioni (CRR) per migliorare la disponibilità dei dati e il ripristino di emergenza nel tuo ambiente SQL Server. La CRR contribuisce a proteggere dalle interruzioni regionali e garantisce la continuità operativa replicando i dati in diverse sedi.

====
.Configurazione di backup
Configura i backup FSx for ONTAP o AWS Backup.

[%collapsible]
====
Configura i backup FSx for ONTAP o AWS Backup per soddisfare i requisiti di conservazione e conformità, evitando flussi di lavoro di backup duplicati.

====
.Quorum del cluster
Configura il quorum per le istanze del cluster di failover.

[%collapsible]
====
Configura correttamente il quorum per le istanze cluster di failover di SQL Server così il cluster può tollerare i guasti previsti dei nodi.

====
.Lettera di unità
Mantieni la stessa lettera di unità su tutti i nodi.

[%collapsible]
====
Usa le stesse lettere di unità su ogni nodo nella tua configurazione di alta disponibilità di SQL Server. Questo rende la gestione più semplice e aiuta il failover a funzionare correttamente.

====
.Impostazioni heartbeat
Regola l'heartbeat per un comportamento di failover stabile.

[%collapsible]
====
Regola le impostazioni del heartbeat per evitare failover non necessari, rilevando comunque rapidamente i guasti reali.

====
.Archiviazione condivisa
Assicurati che entrambi i nodi possano accedere alle LUN iSCSI condivise.

[%collapsible]
====
Tutti i dischi condivisi (iSCSI LUN) devono essere accessibili da entrambi i nodi nel modello di implementazione FCI affinché il failover possa funzionare.

====
.Servizio SQL Server
Convalida l'account di servizio e le dipendenze di avvio.

[%collapsible]
====
Convalida le autorizzazioni dell'account di servizio, il tipo di avvio e le dipendenze per garantire un comportamento affidabile e ad alta disponibilità.

====

.tabella degli slot TCP
Imposta a 128 per i carichi di lavoro Oracle basati su NFS.

[%collapsible]
====
Configura i parametri del kernel per la tabella degli slot TCP a 128 per i carichi di lavoro Oracle in esecuzione su NFS. Questa configurazione consente più operazioni di I/O simultanee, riducendo la latenza in scenari ad alto throughput come l’accesso ai file di dati Oracle. I parametri del kernel regolano il numero massimo di richieste NFS in sospeso su TCP, agendo come la profondità della coda nelle configurazioni Fibre Channel. I valori predefiniti di Linux, tipicamente impostati a 16, non supportano performance ottimali del database.

====
.Opzioni di montaggio NFS - file di database
Utilizza le opzioni di montaggio NFS che ottimizzano le performance per i file di database.

[%collapsible]
====
Utilizza opzioni di montaggio NFS ottimizzate per i file del database. I parametri chiave includono  `rw` per l'accesso in lettura/scrittura,  `bg` per il montaggio in background,  `hard` per tentativi indefiniti in caso di errori e  `proto=tcp` per una consegna affidabile. I valori di  `rsize` e  `wsize` pari a 262144 migliorano le operazioni di I/O di grandi dimensioni, aumentando il throughput, mentre  `nointr` non interrompe le attività di lunga durata. Questa configurazione migliora le performance e la resilienza del database, soprattutto negli ambienti ad alto throughput.

====
.Opzioni di montaggio NFS per la home directory ADR
Utilizza le opzioni di montaggio NFS che ottimizzano le performance per la home directory ADR.

[%collapsible]
====
Utilizza opzioni di montaggio NFS ottimizzate per la home ADR (Automatic Diagnostic Repository), ovvero la directory radice. La home ADR memorizza log e tracce, che beneficiano di opzioni di affidabilità simili a quelle dei file di database principali, ma non richiedono l'opzione di montaggio  `nointr` perché le operazioni sono meno sensibili alle interruzioni.

[%collapsible]

====
.Opzioni di cache NFS
Non disabilitare la cache host nelle implementazioni standalone.

[%collapsible]
====
Ometti le opzioni di montaggio NFS che disabilitano la cache dell'host, come  `actimeo=0` e  `noac`, nelle implementazioni Oracle standalone per migliorare efficienza e affidabilità. Queste opzioni si applicano agli ambienti cluster per garantire la coerenza della cache, ma negli ambienti a istanza singola bypassano inutilmente la cache e possono ridurre significativamente le performance.

[%collapsible]

Questo include la funzionalità di bilanciamento del carico DNS disponibile in ONTAP. Una risoluzione coerente degli indirizzi IP mantiene la stabilità del database e previene potenziali crash o corruzione dei dati.

.file di configurazione dNFS

Verifica e aggiorna il contenuto del file  `oranfstab` per garantire un utilizzo corretto di Direct NFS (dNFS). Il file  `oranfstab` è essenziale per configurare funzionalità dNFS avanzate come il multipathing e opzioni NFS specifiche. Una configurazione corretta migliora l'efficienza dell'accesso e della gestione dei dati.

.dNFS senza cache condivisa
Usa  `nosharecache` per casi specifici di montaggio multiplo.

[%collapsible]
====
Configura l'opzione di montaggio  `nosharecache` per gli ambienti in cui Direct NFS (dNFS) è abilitato e un volume di origine viene montato più di una volta su un singolo server con mount NFS nidificati. Questa configurazione impedisce la condivisione della cache tra i mount, garantendo coerenza dei dati e performance ottimali.

====
Disabilita le Transparent Huge Pages (THP) sugli host che eseguono database Oracle per prevenire un potenziale peggioramento delle performance e migliorare la gestione della memoria.

Abilita le opzioni avanzate del Transmission Control Protocol (TCP).

[%collapsible]

====

Rimuovi il parametro  `db_file_multiblock_read_count`.

[%collapsible]

[[resiliency]]
=== Resilienza

.Snapshot coerenti con l'applicazione
Usa snapshot coerenti con l'applicazione con NetApp SnapCenter.

[%collapsible]
====
Utilizza snapshot coerenti con l'applicazione con NetApp SnapCenter per creare snapshot accurati e affidabili dei dati del tuo volume in un momento specifico. SnapCenter semplifica i backup e ti aiuta a ripristinare rapidamente i dati, riducendo i tempi di inattività e proteggendo i carichi di lavoro critici.

====
.Replicazione interregionale
Proteggi contro le interruzioni regionali.

[%collapsible]
====
Abilita la replica tra regioni (CRR) per migliorare la disponibilità dei dati e il ripristino di emergenza per i tuoi database Oracle. La CRR contribuisce a proteggere dalle interruzioni regionali e garantisce la continuità operativa replicando i dati in diverse sedi.

====
Configura i backup FSx for ONTAP o AWS Backup per soddisfare i requisiti di conservazione e conformità, evitando flussi di lavoro di backup duplicati.
